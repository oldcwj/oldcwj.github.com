## Preservation policy

This inventory is the compatibility baseline for adding Coobbi Web Tools.

- Existing Privacy, Support, Help, and App product URLs must not be deleted, renamed, moved, or redirected as part of the Web Tools project.
- The site currently has no general `/privacy-policy/` or `/help/` route. Those example routes in the product requirements must not be treated as existing URLs.
- The four iOS Privacy and Support URLs below are confirmed by the site owner to be in use by released iOS apps. They are immutable P0 assets.
- All other existing App product routes are treated as externally referenced by default, even when their exact Google Play, App Store, or in-app configuration cannot be inspected from this repository.
- Existing JAR and Jre4Android pages on `coobbi.com` remain in place. The separate-domain product strategy does not authorize moving or deleting them.
- New Web Tools must use new routes and must coexist with every route recorded here.

Risk definitions:

- `CRITICAL`: confirmed external App dependency; an outage or URL change can break a released app or store listing.
- `HIGH`: product, navigation, indexing, or likely external-link asset; preserve the URL and page purpose.
- `MEDIUM`: indexed editorial content or compatibility alias; preserve unless a separately approved migration supplies an equivalent permanent redirect.

## Build and ownership boundaries

The following files are generated by `scripts/build-site.js` and must not be maintained only by editing their rendered HTML:

- `/index.html`
- `/apps.html`
- Every App product `index.html` derived from `data/apps.json`
- `/sitemap.xml`

The following public pages are currently hand-maintained and are not recreated by the build script:

- `contact.html`
- `tutorials.html`
- App Privacy and Support pages
- Tutorial and guide `.html` pages
- `jarfileopener/index.html`, the legacy alias page

Important build risk: `scripts/build-site.js` uses the current date for every generated sitemap entry. A build can therefore report unchanged pages as newly modified. It also rewrites all generated App index pages. Future work should update the generator first whenever generated navigation or page content needs to change.

## SEO and link findings

- All checked-in HTML pages have a canonical URL.
- All canonical content pages have a title, meta description, and H1. The legacy alias intentionally lacks a normal content-page H1 and description.
- Product pages use `MobileApplication` JSON-LD. The homepage uses `Organization`; the Apps page uses `CollectionPage`; two SB3 guides contain article-style structured data.
- `robots.txt` allows crawling and advertises `https://coobbi.com/sitemap.xml`.
- No GA4, Google Tag Manager, Plausible, Umami, `sendBeacon`, or application analytics abstraction was found.
- No missing relative link targets were found in the checked-in HTML.
- The repository records Store URLs and package/App Store identifiers, but it cannot reveal every URL configured in App Store Connect, Google Play Console, or released app binaries. The preservation policy therefore treats all existing product/support/privacy routes as externally referenced.

## Compatibility risks before Web Tools work

1. **Generated file overwrite — HIGH.** Homepage, Apps page, App index pages, and sitemap are generated. Editing only the output will be lost on the next build.
2. **iOS Privacy/Support regression — CRITICAL.** Global navigation or styling changes must not alter their URL, availability, or policy content.
3. **Static-host routing — HIGH.** New pages should use directory `index.html` routes that work on the current host. No server fallback or API runtime should be assumed.
4. **False redirect assumption — MEDIUM.** `.htaccess` is not evidence of an active 301 on GitHub Pages. Preserve the HTML alias until production infrastructure is explicitly verified.
5. **Sitemap timestamp churn — MEDIUM.** A normal build rewrites all generated `lastmod` values to the build date, including unchanged pages.
6. **Domain-role misunderstanding — HIGH.** Existing coobbi.com JAR/Jre4Android content remains an asset even though specialized tools live on other domains.
7. **Navigation breadth — MEDIUM.** Adding Web Tools to every generated and hand-maintained page requires coordinated generator and static-page changes. This should be a separate approved milestone with regression checks.
8. **No current test harness — HIGH.** There is no automated route, parser, DOM, accessibility, or build regression suite. Introduce tests before complex file parsers.
9. **No local Node runtime in the current shell — MEDIUM.** `node` was not available during this audit, so the generator was inspected statically and was not executed. A configured runtime must be used before implementation verification.

## Recommended additive architecture

The current stack is suitable for an incremental MVP. A framework migration is not justified before the product is validated.

Recommended new structure:

```text
file-inspector/index.html
hex-viewer/index.html
strings-viewer/index.html
file-hash-calculator/index.html
assets/tools/css/tools.css
assets/tools/js/core/
assets/tools/js/parsers/
assets/tools/js/workers/
tests/
fixtures/
```

Implementation constraints:

- Keep parsing code independent from DOM rendering.
- Use ES modules and Web Workers where supported; avoid loading parsers on the homepage.
- Use `Blob.slice()` and bounded reads for inspection. Do not assume every file can be loaded with `file.arrayBuffer()`.
- Do not add file upload endpoints or send file names, contents, hashes, paths, strings, or internal metadata to analytics.
- Do not reuse `/jar-file-opener/` as the Web JAR Inspector. Detect JAR in `/file-inspector/` and route advanced inspection to `https://jarfileopener.com/`.
- Add future tool URLs to the generated sitemap without removing or renaming existing entries.
- Initially add only a restrained Web Tools entry to the existing brand homepage; do not replace it with a full-screen file drop zone.
- Keep `/apps.html`, `/tutorials.html`, and every existing product/tutorial route exactly as recorded.

## Milestone 1 entry criteria

Before changing the site shell or adding tools:

1. Confirm the actual GitHub Pages/custom-domain deployment settings.
2. Make a machine-readable baseline of all 39 HTML routes plus `robots.txt`, `sitemap.xml`, and `app-ads.txt`.
3. Add a regression check that verifies each route remains present in the build output and retains its expected canonical.
4. Give the four immutable iOS Privacy/Support pages explicit protected-route assertions.
5. Decide how a reproducible Node runtime and tests will be provided.
6. Freeze the MVP-A acceptance scope separately from the later PE/EXE/DLL milestone.

No existing public page, route, policy text, help/support content, UI, canonical, sitemap entry, or SEO content was changed during this audit.
